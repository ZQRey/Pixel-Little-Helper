# Внутренний мессенджер PixelHelper

Доступен начиная с клиента **1.2.11**, автоматический вход Windows — с **1.2.12**. Сервер настроен на `https://helper.gp1.loc` и хранит историю в PostgreSQL вместе с остальными данными Control Center.

## Начало работы

1. Войдите в Windows под своей доменной учётной записью. Дождитесь автоматического обновления помощника до 1.2.12 или установите соответствующий MSI. Служба проверяет обновления каждый час.
2. Нажмите помощника левой кнопкой и выберите **Мессенджер**.
3. Вход выполняется автоматически под пользователем, от которого запущен помощник. Логин и пароль вводить не нужно. Имя сотрудника появится в верхней части окна.
4. Выберите сотрудника слева. Поиск работает по отображаемому имени AD, логину и филиалу. Для одинаковых имён проверьте логин через поиск и филиал.
5. Напишите текст и нажмите **Отправить** или Enter. Shift+Enter добавляет перенос строки. Максимум — 4000 символов.

В каталоге отображаются активные AD-пользователи Control Center, включая сотрудников, впервые вошедших через окно мессенджера. Для появления нового сотрудника в списке ему достаточно один раз войти. Локальные учётные записи панели не включены. Обычные пользователи могут переписываться без административных прав.

Windows подтверждает личность с помощью Kerberos-билета для `HTTP/helper.gp1.loc`. Сервер проверяет билет, затем читает имя, objectGUID и состояние пользователя в AD через LDAPS. Пароль сотрудника не передаётся и не сохраняется. Сеанс мессенджера хранится только в памяти процесса, действует до 8 часов и автоматически обновляется через 6 часов. При запуске выполняется новый вход; файл сеанса прежней версии удаляется. При сетевой ошибке клиент повторяет попытку примерно раз в минуту. Кнопка **Обновить соединение** повторяет вход немедленно.

На общем компьютере каждый пользователь входит в Windows под своим AD-логином. Автозапуск запускает отдельного помощника в его сеансе. У каждого процесса собственная авторизация и история своего сотрудника; переключение пользователей Windows не меняет учётную запись уже работающего процесса. При выходе из Windows процесс завершится. Не запускайте помощника через «Запуск от имени другого пользователя»: тогда он использует учётную запись этого запуска. Локальный пользователь без доменной личности автоматически в мессенджер не войдёт.

Первый успешный вход сохраняет objectGUID AD в профиле. Переименование этой учётной записи сохраняет её внутренний ID и историю. Новая AD-учётная запись с прежним логином и другим objectGUID не получает чужую историю; в этом случае требуется разбор профилей администратором.

## История и уведомления

Сообщение сначала сохраняется на сервере, затем доставляется через SignalR. Статус **Сохранено** означает, что оно записано в базу; **Прочитано** — что получатель открыл активное окно соответствующего диалога. Закрытый мессенджер продолжает получать сообщения через работающий помощник.

Получатель Offline увидит историю и непрочитанные сообщения после подключения. Клиент переподключается и обновляет состояние; повторная отправка неизменённого текста после сетевой ошибки использует прежний идентификатор, чтобы не создать дубликат. Если отправка не прошла, текст остаётся в поле. Не закрывайте окно до повторной попытки, если хотите сохранить черновик.

Последние 50 сообщений загружаются при открытии диалога. Кнопка **Предыдущие сообщения** загружает более ранние записи. История и прочтение синхронизируются между компьютерами, где сотрудник вошёл в мессенджер.

В облачке над помощником появляются имя отправителя, число непрочитанных сообщений и короткий текст. **Открыть переписку** переводит в нужный диалог. Несколько быстро пришедших сообщений объединяются. Для открытого активного диалога отдельное облачко и звук не нужны.

В верхней части окна можно отключить **Звук**, **Текст уведомления** или включить **Не беспокоить**. На заблокированном рабочем столе облачко и звук не показываются. Звуковое оповещение использует системный звук Windows и зависит от громкости и системных настроек звука.

**Online** в мессенджере означает наличие подключённого сеанса мессенджера сотрудника; это отдельный статус от Online компьютера в Control Center.

## Настройки администратора

В веб-панели откройте **Мессенджер**. Доступ требует права `settings.manage` (у супер администратора оно есть по умолчанию).

- **Включить личную переписку** — разрешает или отключает работу мессенджера. При отключении его текущие соединения завершаются; история сохраняется.
- **Срок хранения сообщений** — 0 означает хранение без ограничения (значение по умолчанию). Можно задать от 30 до 3650 дней. При ежедневной очистке более старые сообщения удаляются; перед сохранением ненулевого срока панель запрашивает подтверждение.
- **Сохранено сообщений** — общее количество записей без раскрытия содержимого.

Содержание диалога через API доступно только его участникам, включая пользователей с административными ролями. Веб-панель не предоставляет просмотр чужой переписки. Данные хранятся в серверной базе; ограничения API не заменяют контроль административного доступа к самой базе и её резервным копиям.

Отключение учётной записи в разделе **Пользователи** прекращает её доступ. Переписка с отключённым сотрудником сохраняется в списке существующих диалогов, но отправка ему новых сообщений запрещена.

## Проверки и ограничения первого выпуска

Проверены сохранение и доставка через настоящий SignalR, работа с Offline-получателем, история и пагинация, непрочитанные сообщения, подтверждение прочтения, отсутствие дубликатов, изоляция третьего пользователя, отключение аккаунта, переименование AD и защита истории от повторного использования логина. Интерфейс входа и диалога проверен через WPF; миграция PostgreSQL выполнена на сервере после резервного копирования.

Поддерживаются личные текстовые диалоги. Групповые чаты, файлы и редактирование сообщений пока не реализованы. Черновики не сохраняются после закрытия окна. Реальный Kerberos-вход и обновление сеанса проверены под zqrey3; разделение двух пользователей и изоляция переписки проверены автоматическими тестами. Практическую проверку переключения Windows на общем компьютере выполните входом двух сотрудников.

## Требования для автоматического входа

- Компьютер состоит в AD, пользователь вошёл под доменным логином и имеет доступ к контроллеру домена. При входе по сохранённым данным вне сети авторизация выполнится после восстановления доступа к AD.
- Адрес клиента — `http://helper.gp1.loc` или `https://helper.gp1.loc`; мессенджер всегда использует HTTPS. Адрес по IP не подходит для Kerberos. Сертификат helper должен быть доверенным на компьютере.
- Время клиента, сервера и контроллера синхронизировано. Допустимое расхождение Kerberos обычно до 5 минут.
- В Control Center включён AD. Для проверки состояния пользователей используются уже сохранённые логин/пароль чтения каталога в настройках Telegram (`litlehelper`); их права — чтение AD. Включать Telegram-уведомления для автовхода не требуется.
- Настройки браузера/GPO для автоматического входа в сайты не требуются: помощник сам использует текущие Windows credentials.

На `dc01.gp1.loc` создана отдельная непривилегированная служебная учётная запись **LHMessengerSSO** со SPN `HTTP/helper.gp1.loc`, шифрованием AES256, запретом делегирования и неистекающим случайным паролем. Это учётная запись службы, а не сотрудника. Не меняйте её пароль отдельно от keytab.

Keytab находится в защищённой папке `C:\ProgramData\HelperMessengerKerberos` на dc01 и в постоянном Docker volume `server-data`, путь `/app/data/kerberos/helper.keytab` на сервере. Папка контейнера имеет права 700, keytab — 600, владелец app (UID 1654). Файл `/app/data/kerberos/krb5.conf` содержит настройки домена; образ устанавливает системную библиотеку Kerberos. После первичной настройки обычный `docker compose up -d --build` сохраняет SSO. При переносе восстановите защищённый volume и DNS, не помещайте keytab в Git.

Проверка на доменном компьютере: `klist get HTTP/helper.gp1.loc`. Если билет не выдаётся, проверьте DNS, связь с DC, время и уникальность SPN. Если билет есть, но автовход не работает, проверьте соответствие keytab паролю службы и параметры чтения AD. Сервер принимает только Kerberos; подмена имени через заголовки и переход на NTLM не разрешены.
