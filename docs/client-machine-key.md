# Ключ компьютера и автоматическое восстановление связи

Исправление включено в клиент 1.2.26 и серверный маршрут `/api/agents/machine-enroll`.

## Причина повторных конфликтов

Раньше ключ создавался и сохранялся в `%APPDATA%\PixelHelper\config.json`. У разных пользователей Windows получались разные ключи одного компьютера. Удаление или повреждение настроек также приводило к созданию нового ключа, который сервер обоснованно отклонял.

На компьютере разработчика обнаружена дополнительная причина: интеграционные тесты клиента могли сохранять свои настройки в папку установленного помощника. Тестовый запуск мог заменить рабочий ключ. Теперь весь набор тестов использует отдельную временную папку. Проверка полного набора тестов подтверждает, что рабочий `config.json` остаётся неизменным.

## Новое поведение

1. Служба `PixelHelperUpdater`, работающая от LocalSystem, создаёт случайный ключ компьютера длиной 48 байт.
2. По HTTPS служба обращается к серверу с Kerberos-аутентификацией от имени **компьютера AD**, а не вошедшего пользователя.
3. Сервер проверяет домен, тип и активность учётной записи компьютера, его имя и `objectGUID` в AD. Обычная учётная запись пользователя для восстановления ключа не подходит.
4. После успешной проверки служба сохраняет ключ в `HKLM\SOFTWARE\PixelHelper`, значение `MachineIdentity`. Значение зашифровано Windows DPAPI с областью LocalMachine. Обычные пользователи имеют доступ к разделу только для чтения; запись выполняет служба SYSTEM.
5. Все сеансы Windows на компьютере используют один ключ из этого хранилища. Пользовательские настройки оформления и учётная запись мессенджера остаются отдельными.
6. При появлении восстановленного ключа работающий клиент перечитывает его и переподключается автоматически. Приоритет имеет ключ компьютера, поэтому неправильный ключ в пользовательском файле больше не блокирует соединение.

Изменение адреса с `http://helper.gp1.loc` на `https://helper.gp1.loc` не меняет область ключа. Другой адрес сервера имеет отдельную область и требует регистрации. Восстановление всегда выполняется через HTTPS, даже если обычный адрес подключения указан как HTTP.

Запись компьютера в Control Center сохраняется: её ID, привязка к супер администратору и связанные данные не удаляются. Сервер хранит хеш ключа; значение ключа не возвращается через веб-панель и не записывается в журнал диагностики восстановления.

## Что требуется при развёртывании через SCCM

- Установить MSI 1.2.26 или новее от SYSTEM.
- Использовать DNS-адрес `helper.gp1.loc`, для которого настроен SPN HTTP/helper.gp1.loc; обращение к IP-адресу не обеспечивает этот Kerberos-механизм.
- Убедиться, что компьютеры включены в AD и доверяют сертификату HTTPS сервера.
- Оставить службу `PixelHelperUpdater` в автоматическом режиме и запущенной. Создание ключа работает даже при отключённой настройке скачивания обновлений.
- На сервере должны работать Kerberos, настройки подключения к AD и настроенная учётная запись чтения каталога.

Команда установки:

```bat
msiexec /i PixelHelper.msi /qn /norestart SERVERURL=https://helper.gp1.loc
```

Отдельные ключи сотрудникам передавать не нужно. После обновления серверной части ранее установленные клиенты переходят на общий ключ при установке новой версии.

## Случаи, требующие администратора

Если объект компьютера в AD удалён и создан заново с тем же именем, его `objectGUID` изменится. Сервер остановит автоматическую замену ключа: администратор должен сначала проверить, что это действительно нужный компьютер. Это защищает существующую запись от подмены по имени.

Компьютеры вне домена и старые клиенты продолжают использовать прежнюю регистрацию. Для них конфликт ключей требует административной регистрации. Отключение проверки ключа или автоматическая замена ключа только по имени компьютера не предусмотрены.

## Проверки исправления

- Полный набор тестов клиента проходит, рабочий конфигурационный файл не меняется.
- Тесты сервера проверяют восстановление старого ключа и повторное восстановление после потери ключа без изменения ID компьютера.
- HTTP, поддельные заголовки, неверный Kerberos, обычный пользователь AD, чужое имя ПК и неверный ключ отклоняются.
- При изменении GUID объекта AD действующий ключ сохраняется, запрос получает конфликт.
- Тесты мессенджера подтверждают совместимость изменения с существующими чатами.
