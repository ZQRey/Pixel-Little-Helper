# Управление заявками GLPI через Telegram

## Настройка

1. В Control Center откройте **Telegram**. Сохраните токен бота, полный Chat ID группы (с минусом) и ID темы, если используется форум.
2. Включите **Отправлять новые заявки в Telegram**.
3. Для чтения AD укажите `litlehelper@gp1.loc` и пароль этой учётной записи. Достаточно чтения пользователей каталога; права администратора домена не нужны. Пароль хранится зашифрованным, пустое поле при повторном сохранении сохраняет прежний пароль.
4. LDAP-атрибут оставьте **physicalDeliveryOfficeName** — это поле «Комната» в вашей AD. Значение — положительный числовой Telegram ID пользователя, например `684257380`, а не имя `@username` и не ID группы. Один ID должен принадлежать ровно одной активной учётной записи.
5. Каждый исполнитель должен один раз войти в Control Center через AD. В разделе **Пользователи** выдайте ему роль администратора/оператора либо отдельные права **Просмотр всех заявок** и **Создание заявок и изменение статуса**. Наличие Telegram ID само по себе прав не выдаёт. Блокировка в панели, отключение AD или отзыв любого из этих прав запрещают дальнейшие действия бота.
6. В GLPI должен существовать активный пользователь с точно таким же коротким логином AD (`zqrey3`, без `@gp1.loc`). Настройте ему профиль технического исполнителя и доступ к соответствующей сущности. API-учётной записи помощника нужны права чтения пользователей/заявок/исполнителей, назначения заявок, добавления ответов/решений и изменения статусов.
7. Сохраните настройки, введите Telegram ID в поле проверки и нажмите **Проверить сопоставление**. Проверка читает AD и GLPI, сообщений не отправляет.
8. Каждый исполнитель открывает бота и нажимает **Start**. Бот не может первым начать личную переписку.
9. Включите **Управлять заявками через бота** и сохраните. Обновите страницу, чтобы увидеть время последней проверки и возможную ошибку бота. Для этого режима нужен отдельный бот: у него не должно быть webhook или другого процесса `getUpdates`. Сервер обращается к Telegram сам; публичный webhook и открытие дополнительных портов не требуются.

## Работа

- В группе у новой заявки есть кнопка **Принять**. Сервер проверяет текущего исполнителя в GLPI, назначает заявку на нажавшего сотрудника и переводит её в работу. При одновременном принятии внутри одного Control Center выигрывает один исполнитель. Уже назначенную другому сотруднику заявку бот не забирает.
- До назначения бот проверяет возможность отправить исполнителю личное сообщение. Если личный чат не открыт или бот заблокирован, назначение не выполняется.
- В личном чате используйте кнопку **Мои заявки** или `/my`. Список показывает назначенные активные заявки, зарегистрированные в Control Center (созданные через помощник или панель). Существующие посторонние заявки GLPI автоматически в Control Center не импортируются.
- В карточке доступны **Ответить**, **Добавить решение**, **В работе**, **Ожидание**, **Закрыть**, **Обновить**. Отображаются исходное обращение и последние пять публичных ответов GLPI.
- После «Ответить» или «Добавить решение» следующее текстовое сообщение сохраняется в выбранную заявку. Режим ввода действует 15 минут; **Отмена** или `/cancel` отменяет его. Фото, голосовые сообщения и вложения пока не поддерживаются.
- Решение создаёт запись ITILSolution в GLPI; закрывать через бота можно только решённую заявку. Правила переходов и права API дополнительно проверяет GLPI.
- Действия выполняются API-учётной записью GLPI. В текст ответа/решения добавляется `[Telegram · логин AD]`, а в журнале Control Center фиксируется действовавший сотрудник. Это не имитация входа сотрудника в GLPI: техническим автором записи в GLPI остаётся API-учётная запись.

## Синхронизация и фильтры

В разделе **Заявки** доступны фильтры: все, активные, в работе, новая, назначена, запланирована, ожидание, выполнена (решена), закрыта. Фильтр применяется на сервере до ограничения списка в 500 записей. Пользователь по-прежнему видит только собственные обращения.

Состояния и назначения из GLPI обновляются фоном: до 30 заявок за проход с интервалом 60 секунд. При большом числе заявок полный обход занимает несколько проходов. Открытие карточки и операции бота дополнительно читают актуальное состояние GLPI. После смены исполнителя непосредственно в GLPI прежний исполнитель не сможет изменить заявку через бота.

Курсор Telegram и обработанные update_id хранятся в БД и переживают перезапуск Docker. Входящие действия не переигрываются автоматически после неоднозначного сбоя, чтобы не создавать повторные ответы/решения. Если процесс оборвался во время действия или GLPI недоступен, откройте заявку в GLPI и проверьте результат перед ручным повтором. Исходящие уведомления о новых заявках используют прежнюю очередь повторной отправки; её состояние доступно в настройках Telegram.

Запускайте один экземпляр приложения, обрабатывающего этого бота. Защита одновременного принятия действует между операциями данного Control Center; GLPI не предоставляет общей атомарной блокировки с изменениями из других интеграций.

## Проверка после настройки

Создайте тестовую заявку через помощник, примите её в группе, отправьте ответ боту, затем добавьте решение. В GLPI проверьте исполнителя, ответ, решение и статус. Закройте заявку через бота и проверьте фильтр **Закрыта** в панели. При попытке другого сотрудника принять уже назначенную заявку бот должен отказать.

Источники: [GLPI REST API V1](https://help.glpi-project.org/documentation/modules/configuration/general/api/api), [Telegram Bot API](https://core.telegram.org/bots/api), [атрибут physicalDeliveryOfficeName](https://learn.microsoft.com/en-us/windows/win32/adschema/a-physicaldeliveryofficename).
